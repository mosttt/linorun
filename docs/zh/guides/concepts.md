# 常用概念

[简体中文](concepts.md) | [English](../../en/guides/concepts.md)

Linorun 管理组件的启动、依赖变化和停止。应用负责具体业务，Linorun 负责在正确的时机
执行已登记的清理工作。写第一个组件只需知道 `mount`、`on_cleanup` 和 `shutdown`；
代码见[开始使用](getting-started.md)。本页解释代码中会遇到的术语，可按任务选读。

## 一个组件可以启动多次

`worker()` 是组件定义，`runtime.mount(worker(), config).await` 启动一个组件实例，返回
控制它的 `FiberHandle`。同一个定义可以挂载多次，每个实例都有独立的配置、状态和资源。

配置更新、显式重启或服务依赖改变，会让同一个实例先结束旧的一次运行，再开始新的一次
运行。句柄保持不变，每次运行持有自己的配置和依赖快照。

| 名称 | 对应什么 | 什么时候需要关心 |
| --- | --- | --- |
| `Runtime` | 一组组件的运行时 | 创建、挂载组件、最后关闭 |
| `Component` | 可反复启动的组件定义 | 写启动逻辑、声明依赖和提供的服务 |
| Fiber | 一次挂载得到的组件实例 | 通过 `FiberHandle` 更新、查询或停止 |
| Episode | 实例从一次启动到清理完毕的过程 | 理解为什么配置和依赖不会中途切换 |
| Effect | 已交给运行时管理的建立与清理工作 | 管理后台任务、连接和其他外部资源 |
| Inverse | effect 对应的清理操作 | 在回调里真正关闭资源 |

日常组件代码直接使用 `ComponentContext`，无需手动创建 Fiber、Episode 或维护清理栈。

## 返回成功代表启动完成

组件的异步函数返回 `Ok(())` 后，组件进入运行状态，其服务和已登记资源仍然有效。
Linorun 保留清理回调，直到依赖变化、重启、停止或整个运行时关闭。

`FiberState` 是供调用者观察的状态：

| 状态 | 含义 |
| --- | --- |
| `Pending` | 尚未具备全部声明的依赖，正在等待 |
| `Loading` | 正在执行启动逻辑 |
| `Active` | 启动完成 |
| `Unloading` | 正在等待依赖边界或执行清理 |
| `Failed` | 启动失败且已完成相应回收 |
| `Disposed` | 该实例已永久停止 |

`mount`、`restart`、`update_config` 返回后，转换可能仍在执行；需要知道结果时调用
`fiber.wait_settled().await`，并检查返回状态。`Pending` 也可能是稳定状态：依赖还没有
出现时，运行时没有进一步工作可做。

## 清理按已登记顺序倒着执行

启动过程是“打开数据库、启动任务、发布服务”，停止过程就需要“撤回服务、停止任务、
关闭数据库”。每一步完成后立即登记对应清理，后登记的先执行。

`ctx.on_cleanup(label, callback).await` 会等到登记完成再返回。同一个组件内，运行时
串行执行清理，每项至多一次；错误会记录在报告中，并继续清理更早的项。独立组件之间
可以并行推进，并不存在覆盖整个 Runtime 的单一清理栈。

`ctx.effect(...)` 则启动受管理的资源建立工作，返回句柄时建立可能还没结束，需要时用
`wait_forward()` 等待。详细写法见[编写组件](../api/component-authoring.md)。

## 服务既是调用接口，也是生命周期依赖

`service_contract!` 定义方法；提供方实现方法并调用 `provide`；使用方在 `requires`
中声明依赖，再用 `ctx.service::<Service>()` 取得客户端。

声明依赖让运行时知道谁必须先停止。提供方整体停止时先撤回服务，新启动不会再选中它；
已经在用它的组件先完成清理，提供方随后才能回收底层资源。子组件不会因为父子关系自动获得未声明
的服务。

一次启动固定其使用的提供方，这份依赖快照称为 **CommittedView**。清理调用旧客户端时
仍访问旧提供方，避免把旧资源交给新提供方关闭。服务值看起来相同，也不表示提供方身份
相同；依赖变更由提供方身份判断。

已有客户端不会自动跟随最新注册切换实现。组件重新启动后取得新客户端。手动撤回单项
注册只等待撤回时实际使用该 Binding 的组件及其当时那次运行；只关注同一服务位置的
组件会收到通知，却不会被等待。原运行结束后，后续重新启动不延长等待，也不等待后代
全部移除。因此这不等同于公共 `wait_settled`；同一提供方恢复时，原运行重新稳定也可以
达到等待边界，继续使用旧客户端。详见
[定义和调用服务](../api/service-contracts.md)。

## 依赖变化在步骤边界生效

正在执行的启动步骤或清理 Future 不会被强行取消。依赖或配置改变时，运行时记住最新
目标，等当前步骤结束再决定继续启动还是清理。规范把这一行为称为 **inertia**。

例如启动步骤等待连接完成时，依赖短暂离开又由同一提供方恢复；到步骤边界时目标重新
一致，就不必为了中间的短暂变化强行重启。分步启动可以让复杂建立过程提供更多检查边界。

在停止请求到来后，已开始的启动或 effect 步骤仍可用 `on_cleanup` 交还刚取得资源的
清理，只要还是同一 Episode 且卸载清理尚未开始。过期 Episode 不再接受登记；这也不
允许启动新的外部工作。

这也意味着 `shutdown` 会等待已经开始的步骤和清理完成。它们若永远不结束，关闭也会
继续等待；停止信号和业务需要的超时由实际持有资源的代码处理。

## Realm 选择服务命名空间

同一个 Runtime 可以同时容纳同一种服务的多个实现。`Realm` 为服务划分命名空间：
“服务类型 + Realm” 决定一个可注册实现的位置，规范中称为 BindingSlot；实际注册称为
Binding。

```rust
let root = runtime.root();
let realm = root.create_realm();
let local = root.isolate::<Database>(realm)?;

local.mount(database(), database_config).await?;
local.mount(worker(), worker_config).await?;
```

这两个组件会在选定的 Realm 提供和寻找 `Database`。其他服务继续使用原来的命名空间；
需要隔离几种服务，就分别调用几次 `isolate`。Realm 必须由同一个 Runtime 创建。

`isolate` 返回一个派生上下文，不修改原上下文，也不让已有客户端切换提供方。它提供
进程内服务命名空间隔离；进程、文件系统、网络或租户权限隔离由宿主环境负责。

## Intercept 给调用附加信息

服务契约可定义调用元数据，例如日志标签、追踪标识或应用策略。`intercept::<Service>`
派生带附加信息的上下文，服务实现从 `CallContext.intercept` 读取合并后的值。

合并规则由该服务自己定义，Linorun 不把字段自动解释为超时或权限规则。没有这类需求时，
契约使用默认的 `()` 即可。Intercept 不改变所选服务的命名空间。

## 观察状态与关闭运行时

`runtime.snapshot().await` 返回同一时刻一致的组件、依赖与资源状态；可选的事件记录
用于追踪启动、撤回和清理顺序。组件测试可以使用[确定性测试工具](deterministic-testing.md)
逐步推进异步工作，无需依赖 sleep。

关闭单个组件用 `fiber.dispose().await`，关闭所有组件和宿主资源用
`runtime.shutdown().await`。检查返回报告里的 `cleanup_errors`，完成后再退出应用。
句柄可以克隆和丢弃，但丢弃句柄不承担异步清理。

需要实现自定义适配器或审查底层状态机时，再阅读 [Core API](../api/core-api.md)、
[核心数据模型](../architecture/data-model.md)和 [运行时规范](../reference/runtime-specification.md)。
这些进阶资料保留完整的内部术语和状态转移，普通组件可以从上面的任务入口开始。
