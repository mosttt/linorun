# Conformance testing strategy

[简体中文](../../zh/testing/conformance-strategy.md) | English

## 1. Acceptance goals

Tests establish state-machine semantics rather than line coverage. Core 0.1 acceptance covers:

- The specified O-Insert/O-Retire/O-Remove and L-Begin through L-Unload;
- the seven core invariants;
- resource cleanup, iteration, inertia, service resolution, and isolation behavior;
- CommittedView, the withdrawal guard, and failure transitions;
- Rust public API type boundaries, Send/Sync, panic conversion, and macro expansion.

Race scenarios use controlled Futures/Streams or reducer inputs, never sleeps.

## 2. Test layers

### 2.1 Pure-state unit tests

Tests in `lifecycle.rs`, `topology.rs`, `route.rs`, and the effect adapters directly verify:

- Begin/Iter/Finish/Divert/Raise/Leave/Unload;
- revision and pending failure outcomes;
- Target comparisons using only Provider identity;
- fixed endpoints/bindings in CommittedView;
- BindingId-matched deletion during Slot replacement;
- nearest-isolate selection and intercept fold order;
- the `has_next` boundaries of Once/Iter/Steps.

These tests do not start a Runtime Actor.

### 2.2 Actor/Core unit tests

Internal tests in `runtime/tests.rs` can observe crate-private records and cover:

- the shared sequence of EffectRecords and the Episode accumulator;
- Core-owned mount/provide actions;
- running ownership in the cleanup scheduler;
- report collectors;
- snapshot projections;
- stale completion-token checks;
- the shutdown Root episode.

User forward, activation, and inverse code is always polled in tasks. Tests do not call it directly from inside the Actor.

### 2.3 Deterministic public API tests

`linorun-testkit::DeterministicExecutor` implements the production `TaskSpawner` interface. Its safe `ArcWake` queue manually polls tasks, allowing precise control over:

- whether the Actor processes dispose or accepts completion first;
- when activation/effect steps land;
- when inverses finish;
- which boundary receives a Binding replacement;
- whether a snapshot observes state before or after a transition.

`Scenario::run` advances the outer API Future together with Runtime tasks. When no task is runnable, it returns `DriveError`, indicating a real pending boundary in the test.

### 2.4 Downstream macro fixtures

`linorun-macros/tests/generated_api.rs` and `authoring.rs` compile and execute generated code as separate downstream crates, verifying:

- the unique static descriptor generated by `component_descriptor!`;
- the contract-local Client generated by `service_contract!`;
- connectivity between the Provider trait object, erased adapter, and typed methods;
- `Context::service::<C>()` returning `C::Client`;
- actual delivery of declared/route intercepts to the endpoint;
- representative identity and associative merge values;
- `#[component]` and `#[service_impl]` generated setup, calls, and cleanup using the same public API;
- downstream type boundaries when macros are imported through Core's re-exports.

Generated code adds no inherent impl to the external `ServiceRef<C>` type.

### 2.5 Runnable examples and rustdoc

All-target testing compiles:

- `linorun-core/examples/reversible_component.rs`;
- `linorun-core/examples/hello.rs`;
- `linorun-core/examples/application.rs`;
- `linorun-macros/examples/typed_service.rs`;
- all integration tests.

rustdoc is built with `-D warnings` to check Rust paths and intra-doc links.

### 2.6 Convenient component entry points

`authoring_context.rs` verifies, through public APIs, serial LIFO across consecutive cleanup registrations, at-most-once early disposal, derived Context routing and resource ownership, Consumer cleanup using the old endpoint, and inertia when registration races with shutdown. It uses the deterministic executor rather than introducing a separate runtime simulation for convenience APIs.

## 3. linorun-testkit

### DeterministicExecutor

Each spawned task exclusively owns its Future in an Arc task cell. The waker only requeues that cell. `run_one` polls one task at a time. Once the Future is Ready, it is removed from the cell and the active count decreases.

This directly exercises driver continuation ownership: Actor and task never hold the same driver at once, and a new iteration can only be spawned after the Actor accepts the preceding completion.

### controlled and step_stream

- `controlled<T>()` returns a single-use `Control<T>` and a `Controlled<T>` Future.
- `step_stream<T>()` returns a pushable/closable `StepSender<T>` and Stream.

Control can be cloned, but only one `complete` succeeds, making it useful for completion races.

### TraceRecorder

RuntimeBuilder's standard-library event sender connects to `TraceRecorder`. `drain` preserves Actor sequence. `event_tag` supplies coarse labels without discarding the original payload.

### Snapshot checker

`check_snapshot` verifies at each observation point:

- bidirectional parent/children consistency;
- the synthetic Root and live child mount-effect ownership;
- unique BindingIds, visibility, owner effect, and committed consumer indexes;
- bidirectional agreement between `relied_by` and CommittedView Provider edges;
- Episode/Effect identities and complete agreement between Effect inverse projections and the Episode accumulator;
- unique inverse sequences within each Fiber;
- at most one running inverse per Fiber.

`snapshot_validation.rs` starts from actual Runtime snapshots, introduces duplicate BindingIds and missing/duplicate/reordered inverse projections, and checks Armed, Running, and completed snapshots. It verifies structural validation, not an entire execution history.

`normalize_snapshot` provides coarse structural comparisons. It retains Fiber state, Provider/parent relationships, Binding identities, and Effect inverse sequences, but omits RuntimeState, EpisodeId, revision, step identities, Effect phase, Realm, and error text. Assert directly against the complete RuntimeSnapshot when those semantics matter. Equal normalized snapshots do not imply equal complete runtime states.

### ReferenceModel

`ReferenceModel` stores its own ModelFibers, ModelBindings, and ModelEffects. `ModelCommand` explicitly represents lifecycle, bindings, consumer edges, effects, yields, and inverse start/finish.

The model rejects illegal phases, duplicate Fiber-local sequences/identities, parallel inverses, selection of a non-maximum requested sequence, and O-Remove while the Fiber is installed or retains children/Bindings/Effects. FinishUnload requires running inverses, live Effects, Bindings, and the Fiber's consumer relationships to have been explicitly cleared. Rejected commands preserve the original record. It holds neither Runtime containers nor an executor and does not reuse production records.

Limitation: scenarios currently submit `ModelCommand` explicitly. This is not a complete differential model that automatically replays Runtime events. It establishes the independent transition oracle's rules and rejection of invalid transitions. Runtime conformance must also be assessed through the snapshot checker, event-order assertions, and scenario catalog below; it cannot be inferred from model tests alone.

The model stores no Target/revision/StepId and does not represent CommittedView survival after Binding withdrawal. Scenarios must supply the explicit retry behind Begin and key equality behind Finish; StartInverse cannot independently establish the withdrawal guard. `model_boundaries.rs` verifies terminal conditions the model can express and atomic rejection. These tests are not a complete formal proof.

## 4. Structural checks at each step

### Descriptors and contracts

- The descriptor is a unique `'static` instance.
- Config TypeId equals `Component::Config`.
- Requirement ServiceIds are unique and ordered stably.
- provides has no duplicates.
- Runtime-local ServiceId mappings have consistent Contract/Intercept TypeIds.
- Contract identity/merge are pure value operations satisfying their algebraic laws.

### Fibers and Episodes

- A parent exists, with symmetric child.parent and parent.children.
- Root has neither parent nor mount effect and is never removed.
- An ordinary, non-retired child's mount_effect refers to its parent Episode entry.
- A Fiber has at most one installed Episode.
- Inactive holds no CommittedView.
- Removed Fibers appear in no Binding, watcher, or children collection.

### Bindings and CommittedViews

- Each ServiceId+RealmId Slot contains at most one Binding.
- A Binding's Provider and owner effect exist.
- A visible Binding's Provider is Active and not retired.
- Replacement deletion matches BindingId.
- CommittedEntry order matches Requirement order.
- Key, binding, endpoint, and declared intercept remain fixed throughout an Episode.

### Effects and inverses

- seq is unique within a Fiber and allocated in the order the Actor accepts Yield completions.
- Only an accumulator entry holds each armed InverseFn.
- A Fiber has at most one running inverse.
- The scheduler selects the maximum seq from the currently requested Armed set.
- The running inverse lands before another is selected.
- Completing an Effect requires no remaining entry in the accumulator/cleanup_running; record removal and completion publication occur in the same turn.
- An empty effect produces no placeholder inverse.

## 5. Seven core invariants

### I1: An inverse runs at most once

Tests attach counters to inverses and assert after manual disposal, Fiber unload, shutdown, and panic/error paths:

~~~text
calls[inverse] <= 1
~~~

### I2: Fiber-local serial LIFO

Event assertions between consecutive cleanup actions:

~~~text
InverseStarted(max requested seq)
< InverseFinished(same seq)
< InverseStarted(next max seq)
~~~

If manual disposal already started a lower sequence, inertia lets it land first. Only then is the maximum selected again from the remaining set.

### I3: Bindings leave resolution first

A Provider's `LLeave/BindingRemoved` occurs before its first whole-Fiber `InverseStarted`. Snapshots never show a visible Binding from a non-Active Provider.

### I4: Consumers before Providers

Chain and branch tests assert that all installed Consumers finish L-Unload before the Provider starts its accumulator. A chain yields `C cleanup < B cleanup < A cleanup`.

For manual Binding withdrawal, `manual_withdrawal_cycles.rs` verifies that Loading Fibers which merely watch the Slot without committing that BindingId cannot form a Core inverse wait cycle. `withdrawal_episodes.rs` uses two actual Consumers to verify capture of `(FiberId, EpisodeId)`: one remains in its old Episode while the other has entered a new Loading Episode on a replacement Provider. Once the former leaves, the old withdrawal does not wait for the latter's new Episode. The file also verifies that same-provider republication can preserve the original Episode and CommittedView while allowing withdrawal to complete.

These regressions assume fixed CommittedViews, visibility of only Active Providers to new Episodes, and the rule that a Provider cannot begin whole-Fiber cleanup while a committed Consumer remains installed. Capturing actual dependencies and Episode identities prevents this withdrawal from adding unrelated wait edges. These tests are not a complete proof of termination for arbitrary user Futures or external wait relationships.

### I5: Fixed CommittedView

Same-provider rebind, Provider switching, and cleanup calls compare BindingId/endpoints to show that old episodes do not read the new Binding store.

### I6: Target uses only Provider identity

- Internal value changes within the same Provider do not reload.
- Equal values from different ProviderIds cause divert/reload.
- Same-provider BindingId replacement that restores Target at the boundary preserves the old Episode.

### I7: One transition per Fiber

Tests submit Target churn, restart, and dispose during controlled Loading. Snapshots always contain one Episode and one running activation step. Completion decisions use only the latest key when the step lands.

## 6. Trace partial order

The main partial order is:

~~~text
Provider LLeave
< BindingRemoved
< Consumer LLeave/LDivert
< Consumer LUnloadFinished
< Provider InverseStarted
~~~

Core-owned effects:

~~~text
provide: EffectStarted < BindingInstalled < [BindingVisible] < EffectForwardCompleted
mount:   EffectStarted < FiberInserted < EffectForwardCompleted < [child LBegin]
~~~

They have no StepId and emit no EffectYielded. Each EffectId emits `EffectDisposeRequested` at most once.

## 8. Workspace acceptance commands

~~~bash
cargo fmt --all -- --check
cargo test --workspace --all-targets --all-features --locked
cargo test --workspace --all-targets --all-features --release --locked
cargo test --workspace --doc --locked
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --all-features --no-deps --locked
~~~

These commands are for full release acceptance. Everyday changes select tests according to their affected scope. Runtime behavior must be covered in both Debug and Release to prevent side effects inside debug assertions from hiding release-build regressions. Doctests run separately. Examples must actually be executed to demonstrate their flows; `--all-targets` only proves that they compile.

## 9. GitHub Actions

The [CI workflow](../../../.github/workflows/ci.yml) runs on pushes to `main` and when pull requests
are opened or updated. It also supports manual runs from the GitHub Actions page.
`rust-toolchain.toml` specifies the Rust version and components; Cargo commands use `--locked`
to preserve dependency resolution.

Ubuntu checks formatting, Clippy, and API documentation, treating Clippy and rustdoc warnings
as failures. Linux, Windows, and macOS each run the full workspace tests in Debug and Release,
doctests, and all four runnable examples. Platforms report independently; a failure on one
does not cancel the others.

The workflow caches Cargo downloads and build output, separating caches by job, operating system,
architecture, toolchain, and lockfile. A new commit on the same branch cancels an older running
workflow. Actions are pinned to commits, and the workflow needs only read access to the repository.
